# BR-003：Preset 增量更新机制（生命周期护栏 - 支柱 B）

<!-- source: strategy-phase2-M2.B.1, planned -->

> **归属**：Phase 2 生命周期护栏战略 — **支柱 B（升级路径）**
>   - 支柱 A（漂移检测）：`/audit-context` 升级 + SessionStart hook
>   - 支柱 B（升级路径）：**本需求** — Preset 增量更新机制
>   - 支柱 C（质量门禁）：hooks 模板库 + 安全加固组件
> **战略定位**：解决"Preset 迭代无法下发到已存量用户"这一生命周期问题,是三支柱中唯一建立"用户长期关系"的能力
> **优先级**：P0(Phase 2 首要里程碑)
> **就绪度**:40%(需求方向明确,技术方案待细化)
> **灵感来源**:Copier (`copier update`)、答案文件持久化模式

---

## 1. 问题陈述

**当前状态**：用户通过 `init.sh` 或 `/init-context` 生成 `.claude/` 目录后，preset 与用户项目之间**无持续关系**。一旦生成，用户要获取 preset 新版本的改进，只能手动对比或重新初始化（会丢失自定义）。

**影响**：
- 用户装完即走，无长期价值捕获 → Stars 不等于真实采用
- 项目对 preset 的迭代改进无法传达到已存量用户
- 缺乏差异化护城河 —— 任何"模板 + 一次性初始化"竞品都可快速复制本项目

**战略意义**（战略文档 §9.2 护城河策略 v2 版本）：
> 中期（v2.x）：从"一次性生成器"升级为"持续上下文守护者"
> → 增量更新（支柱 B）：Preset 更新机制（借鉴 Copier）建立用户长期关系

**与其他支柱的关系**：
- **支柱 A 依赖**：`/update-context` 应在 update 后自动运行漂移检测（`/audit-context`），验证新结构仍对齐
- **支柱 C 协同**：update 操作可被 pre-commit hook 阻断，防止未评审的大量变更直接合入

---

## 2. 用户故事

**主故事**：作为已使用 claude-context-templates 的开发者，我希望能以非破坏方式获取 preset 的最新改进，以便在保留我对 `.claude/` 的自定义的同时持续受益于项目迭代。

**次要故事**：作为团队 Lead，我希望能把 preset 升级操作作为一次可审计的 PR（而非"重新 init + 手动改"），以便团队评审更新内容。

---

## 3. 验收标准

### MVP 范围（必须）

- [ ] 生成 `.claude/` 时记录 `.preset-meta.yml`（preset 名、版本、hash、用户变量值）
- [ ] 新增 `/update-context` 命令（Plugin 路径）
  - 读取 `.preset-meta.yml` 识别当前 preset 和版本
  - 对比用户本地文件 vs preset 新版本，生成三向 diff（base / local / upstream）
  - 对**未被用户修改**的文件：自动应用新版本
  - 对**用户已修改**的文件：交互式询问（保留 / 应用新版本 / 手动合并）
- [ ] 用户变量（从 `project-config.md` 收集的值）自动填入新模板，无需重新询问
- [ ] CI 验证：update 后的项目仍能通过 `/audit-context`

### 可选（Phase 2.1.x 迭代）

- [ ] Shell 版 `update-context.sh` 镜像 Plugin 命令能力
- [ ] Dry-run 预览模式：仅显示会变更什么，不实际修改
- [ ] 基于 git 的自动备份：update 前创建分支

---

## 4. 业务规则

1. **非破坏原则**：update 永远不覆盖用户已修改的内容，除非用户明确选择
2. **元数据不可伪造**：`.preset-meta.yml` 的 hash 由工具计算，防止误触发
3. **版本跨度容忍**：用户可能跨越多个 preset 版本（如 v1.0 → v1.3），需正确处理累积 diff
4. **变量值持久化**：首次生成时收集的用户变量值（项目名、描述等）永久记录，update 不重复询问

---

## 5. 非功能需求

### 可用性
- update 操作在 3 个以内的交互回合内完成（对"无冲突更新"场景）
- 冲突场景每次展示的信息量 ≤ 20 行（避免信息过载）

### 可靠性
- update 失败时可回滚到操作前状态
- 元数据文件损坏时降级为"警告并询问用户是否重置"

### 可测试性
- 提供 3 个以上的典型 update 场景作为 CI 回归用例：
  - 无冲突（用户未修改任何文件）
  - 部分冲突（用户修改了 1-2 个规则文件）
  - 全冲突（用户大幅自定义）

## 6. 技术方案要点（待细化）

### 元数据格式（草案）
```yaml
# .claude/.preset-meta.yml
schema_version: "1.0"
preset:
  name: python-fastapi
  version: "1.2.0"
  generated_at: "2026-04-20T10:00:00Z"
  language: zh-CN
variables:
  PROJECT_NAME: "my-service"
  PROJECT_DESC: "..."
  COVERAGE_MIN: "80"
files:
  "rules/testing.md":
    source_hash: "sha256:abc..."       # 生成时的 preset 原始 hash
    user_modified: false                # 工具维护，用户修改后更新
  "rules/architecture.md":
    source_hash: "sha256:def..."
    user_modified: true                 # 用户已修改标记
```

### Diff 策略
参考 Copier：三向合并（git merge-file 或等价算法）
- base = 生成时的 preset 版本
- local = 用户当前文件
- upstream = preset 新版本

### 交互决策树
```
用户 run /update-context
├─ 读 meta.yml → 识别当前版本
├─ fetch 最新 preset（从 Plugin 或网络）
├─ 对比每个文件的 hash
│  ├─ 未变化 → skip
│  ├─ 仅 preset 变化（用户未改）→ 自动应用
│  ├─ 仅用户变化（preset 未改）→ skip
│  └─ 两边都变化 → 三向 diff 交互合并
└─ 更新 meta.yml
```

## 7. 风险与假设

| 风险 | 概率 | 缓解 |
|------|------|------|
| 用户对 hash 校验不敏感，篡改后无感知 | 中 | update 时显式提示"用户已修改"文件 |
| 跨大版本更新逻辑复杂（v1.0 → v2.0） | 高 | MVP 只支持单版本跨度，大版本跨度给出迁移脚本 |
| `.preset-meta.yml` 放在 `.claude/` 内会被用户误删 | 中 | 文档明确说明，删除后 update 提示重置 |
| 增量更新引入 bug 导致用户 `.claude/` 损坏 | 低 | 强制 git 备份 + dry-run 默认 |

### 关键假设
- 用户倾向"保留自定义"而非"获取最新" → 需验证（v1.0 用户访谈）
- Plugin 能可靠获取 preset 最新版本 → 依赖 Plugin 分发机制
