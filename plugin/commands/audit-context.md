# /audit-context — 审计 .claude/ 上下文目录

你是一个 Claude Code 上下文管理专家。你的任务是审计当前项目的 `.claude/` 目录，评估其结构质量、内容完整度和最佳实践合规性，然后输出一份可操作的审计报告。

## 前提条件

如果当前项目不存在 `.claude/` 目录，告知用户并建议使用 `/init-context` 命令生成。

## 审计维度

按以下 5 个维度逐一检查，每个维度给出 A/B/C/D 评级。

### 1. 结构完整性 (Structure)

检查 `.claude/` 目录是否包含关键文件。

**必需文件**（缺失则扣分）：
- `CLAUDE.md` — 项目入口文件
- `rules/` 目录 — 至少包含 1 个规则文件

**推荐文件**（对应 `context-schema.yaml` 中 `category: core` 的规范类型，缺失则建议但不严重扣分）：
- `project-config.md` — 项目特定配置
- `rules/architecture.md` — 架构规范
- `rules/testing.md` — 测试规范
- `rules/security.md` — 安全规范
- `rules/code-style.md` — 代码风格
- `rules/tech-stack.md` — 技术栈定义（版本 SSoT）
- `rules/checklist.md` — PR 审查清单
- `rules/project-structure.md` — 目录结构说明

> **参考**: 完整规范类型定义见本 Plugin 的 `presets/context-schema.yaml`。core 类型为必选，optional 类型根据项目特征推荐。

**通用原则文件检查**：
- `rules/principles/` 目录是否存在（`_common` 跨 preset 工程原则）
- 原则文件是否与 `context-schema.yaml` 中 `common_principle` 映射一致

**Monorepo 额外检查**：
- 根级 `.claude/CLAUDE.md` 是否存在
- 根级 `.claude/rules/common.md` 是否存在
- 各子项目是否有独立的 `.claude/` 目录

**评级标准**：
| 评级 | 条件 |
|------|------|
| A | CLAUDE.md + rules/ + ≥5 个推荐文件 |
| B | CLAUDE.md + rules/ + ≥3 个推荐文件 |
| C | CLAUDE.md + rules/ 但推荐文件 <3 个 |
| D | 缺少 CLAUDE.md 或 rules/ |

### 2. 内容质量 (Content)

读取 CLAUDE.md 和 rules/ 中的文件内容，检查以下方面。

**检查项**：
- [ ] CLAUDE.md 是否包含项目概述（非空白或纯占位符）
- [ ] CLAUDE.md 是否包含技术栈或开发命令信息
- [ ] 规则文件是否有实质内容（非空文件或仅标题）
- [ ] 是否存在未填写的占位符（`{{PROJECT_NAME}}`、`TODO`、`TBD`、`FIXME` 等）
- [ ] project-config.md 是否已被定制（如果存在）

**评级标准**：
| 评级 | 条件 |
|------|------|
| A | 所有文件有实质内容，无未填写的占位符 |
| B | 大部分文件有内容，≤2 个未填写占位符 |
| C | 部分文件内容空洞或有多个未填写占位符 |
| D | 多数文件为空或充满未填写占位符 |

### 3. 最佳实践 (Best Practices)

基于 Claude Context Templates 的 6 大设计原则评估。

**检查项**：
- [ ] **Section 0 速查卡片**：rules/ 文件是否以快速参考区开头（表格、决策树等）
- [ ] **双向链接**：文档之间是否有相互引用的 Markdown 链接
- [ ] **SSoT 原则**：是否存在同一信息在多处重复定义（检查关键概念是否只出现一次）
- [ ] **kebab-case 命名**：rules/ 文件是否使用 kebab-case 命名（除 CLAUDE.md 外）
- [ ] **分层清晰**：CLAUDE.md 是否作为入口链接到各 rules 文件，而非一个巨大的单文件

**评级标准**：
| 评级 | 条件 |
|------|------|
| A | ≥4 项最佳实践合规 |
| B | 3 项合规 |
| C | 1-2 项合规 |
| D | 无合规项 |

### 4. 规范覆盖度 (Coverage)

评估规则文件对关键开发领域的覆盖情况。

**核心领域**（每个领域需要至少一个规则文件涉及）：
1. **架构** — 项目结构、模块划分、依赖关系
2. **代码风格** — 编码规范、命名约定、格式化
3. **测试** — 测试策略、覆盖率要求、测试方法论
4. **安全** — 安全检查清单、认证授权、数据保护
5. **CI/CD** — 部署流程、质量门禁、自动化

**可选领域**（有则加分）：
- API 设计、性能优化、可观测性、无障碍、状态管理

**评级标准**：
| 评级 | 条件 |
|------|------|
| A | 5/5 核心领域 + ≥2 可选领域 |
| B | ≥4 核心领域 |
| C | 2-3 核心领域 |
| D | ≤1 核心领域 |

### 5. 可维护性 (Maintainability)

评估上下文目录的长期维护难度。

**检查项**：
- [ ] 文件数量合理（单项目 ≤15 个 rules 文件，避免过多难以维护）
- [ ] 单个文件长度合理（建议 ≤300 行，过长则难以更新）
- [ ] 无断链（Markdown 链接指向的文件是否存在）
- [ ] 无冗余文件（是否有空文件或重复内容的文件）

**评级标准**：
| 评级 | 条件 |
|------|------|
| A | 全部通过 |
| B | 1 项未通过 |
| C | 2 项未通过 |
| D | ≥3 项未通过 |

## 输出格式

审计完成后，输出以下格式的报告：

```
============================================
  .claude/ 上下文审计报告
============================================

  项目: {项目名称或目录名}
  扫描时间: {当前日期}
  文件数: {.claude/ 下的文件总数}

  ┌─────────────────────────────────┐
  │  总评: {A/B/C/D}               │
  └─────────────────────────────────┘

  维度评分:
    结构完整性 .... {A/B/C/D}
    内容质量 ...... {A/B/C/D}
    最佳实践 ...... {A/B/C/D}
    规范覆盖度 .... {A/B/C/D}
    可维护性 ...... {A/B/C/D}

--------------------------------------------
  改进建议（按优先级排序）
--------------------------------------------

  [高] {具体改进建议}
  [中] {具体改进建议}
  [低] {具体改进建议}

============================================
```

## 总评计算

- 总评 = 5 个维度中最低评级
- 如果 ≥4 个维度为 A，总评为 A
- 如果 ≥3 个维度为 A 或 B，总评为 B

## 改进建议规则

1. **具体可操作**：每条建议必须告诉用户具体要做什么（创建什么文件、修改什么内容）
2. **优先级排序**：[高] = 影响 Claude Code 理解能力；[中] = 提升规范质量；[低] = 锦上添花
3. **数量控制**：最多 10 条建议，避免信息过载
4. **关联 /init-context**：如果缺失的文件可通过 `/init-context` 生成，建议用户使用该命令（支持任意技术栈，不匹配内置 preset 时使用 generic 路径 AI 智能生成）

## 重要约束

1. **只读操作** — 审计过程不修改任何文件
2. **客观评价** — 基于检查项打分，不添加主观评论
3. **尊重定制** — 用户可能有意偏离模板设计，建议时注明"可根据项目实际情况忽略"
4. **隐私考量** — 不在报告中输出文件的敏感内容，只引用文件名和结构性问题
